# 项目负责人：GitHub 原生协作配置

本指南建议按团队现状逐项配置。Skill 不会代替负责人更改仓库设置，也不要求一次性启用所有功能。

## 1. 成员权限

- 给每个人自己的 GitHub 账号，按工作所需授予最低权限；只报告问题的人通常只需可访问/报告问题，修改仓库文件的人需要写入权限。
- 私有仓库要邀请成员并处理组织 SSO/审批要求。邀请由成员本人在 GitHub 接受。
- 不共享账号、密码、MFA 码或 PAT。

## 2. Issues：共享任务记录

- 启用 Issues，添加清楚的 Issue 模板，至少收集背景/现象、目标、预期成果和可观察的验收方式。
- 只创建团队确有用途的标签，例如 `bug`、`feedback`、`research`。避免把标签体系做成复杂流程。
- 为大型任务启用 Issue Types、父子任务或阻塞关系前，先确认订阅计划和团队真正需要。
- 不强制所有非代码工作创建 PR；可以在 Issue 中保留报告、反馈或链接。

## 3. Projects：可选看板

若团队确实需要跨 Issue/PR 查看计划，可使用 GitHub Projects 原生表格/看板视图，并从少量状态开始。明确谁负责维护状态。Projects 不是 Skill 的依赖；成员或工具没有 `read:project` 权限时，Skill 必须说明无法读取。

## 4. PR、Reviews 和代码责任

- 用 PR 模板要求摘要、关联任务、验证结果、截图/演示（适用时）和部署/数据影响。
- 用 CODEOWNERS 指明真正负责的人/团队，并要求 Code Owner review 前先确认团队可以承担。
- 至少由另一位合适成员审阅自己的代码或重要文档；AI 建议不等于人类批准。
- 用 Issue 关联语法（如 `Fixes #123`）时，只在合并应关闭该任务的情况下使用。

## 5. Rulesets / branch protection

对默认分支要求通过 PR 合并。按团队能力设置必需审阅数、Code Owner、必需状态检查、禁止强推和删除默认分支等规则。设置前查看当前规则与 GitHub 订阅限制。先在非关键分支验证，避免规则把团队锁在仓库外。Skill 服从 GitHub 的实际拦截，不会绕过。

## 6. Actions / 检查

添加最小且可信的自动检查（如 lint、测试、文档链接检查），通过 PR 的 Checks 呈现。审查第三方 Action 来源、固定版本、权限和 secrets 使用；不要给不可信 PR 暴露高权限凭据。没有自动检查时，明确由谁验收、怎么手工复核。

## 7. 初始化核对清单

- [ ] README 有面向新成员的“从哪里开始”。
- [ ] `AGENTS.md` 记录项目专属 agent 行为，而非通用 GitHub 教程。
- [ ] `CONTRIBUTING.md`/Issue/PR 模板讲清楚工作流与验收。
- [ ] Issues 可用于反馈和任务；标签保持精简。
- [ ] 负责人和团队权限正确，私有数据边界清楚。
- [ ] 默认分支规则、必需审阅和 Actions 与团队实际维护能力匹配。
- [ ] 复测非技术成员能否仅用自然语言报告问题、提交研究成果并处理反馈。

此 Skill 只提供通用操作规则，不会自动向仓库添加以上配置。
